## 1. Архитектура

```
Frontend (React + Vite + TS)  →  Cloud Functions (Python 3.11)  →  PostgreSQL
         src/                          backend/                      31 таблица
                                          ↓
                                    S3 (файлы, CDN)
```

**Слои:**

| Слой | Расположение | Назначение |
|------|--------------|------------|
| Интерфейс | `src/components`, `src/pages` | Экраны и элементы управления |
| Логика данных | `src/lib` | Хуки, работа с API, черновики |
| Типы | `src/types/geo.ts`, `src/components/report/reportTypes.ts` | Модели |
| Backend | `backend/references`, `backend/upload-file` | HTTP-функции |
| БД | `db_migrations/` | Схема (7 миграций) |

**Правила:** SQL только в backend. Секреты только в backend (`os.environ`).
Frontend обращается к backend по HTTP, URL берутся из `backend/func2url.json`.

Объём: ~19 300 строк, 44 компонента раздела отчёта, 7 компонентов справочников.

## 2. Модели данных

### 2.1 Справочники

Общие для всех отчётов. Хранятся в отдельных таблицах с обычными колонками.

#### Customer — заказчик
| Поле | Тип | Смысл |
|------|-----|-------|
| `id` | string | Идентификатор |
| `name` | string | Наименование организации |
| `director` | string | ФИО директора |
| `inn` | string | ИНН |
| `address` | string | Почтовый адрес |

#### Contractor — исполнитель
| Поле | Тип | Смысл |
|------|-----|-------|
| `id` | string | Идентификатор |
| `name` | string | Наименование организации |
| `director` | string | ФИО директора |
| `chiefGeologist` | string | ФИО главного геолога |
| `responsible` | string | ФИО ответственного исполнителя |
| `executors` | `Executor[]` | Список специалистов (хранится как JSON) |

#### Executor — специалист (внутри Contractor)
| Поле | Тип | Смысл |
|------|-----|-------|
| `id` | string | Идентификатор |
| `lastName` | string | Фамилия |
| `initials` | string | Инициалы |
| `position` | string | Должность |
| `degree` | string | Учёная степень |

#### License — лицензия на недропользование
| Поле | Тип | Смысл |
|------|-----|-------|
| `id` | string | Идентификатор |
| `number` | string | Номер лицензии (например, `ЯРЛ 57970 ВЭ`) |
| `issueDate` | string | Дата выдачи |
| `ownerId` | string | **Ссылка на `Customer.id`** — владелец |
| `siteName` | string | Наименование участка недр |
| `useType` | string | `search_eval` (поиск и оценка) / `exploration_mining` (разведка и добыча) |

#### Contract — контракт
| Поле | Тип | Смысл |
|------|-----|-------|
| `id` | string | Идентификатор |
| `number` | string | Номер контракта |
| `date` | string | Дата |
| `name` | string | Наименование |

### 2.2 ReportData — карточка комплекта

Главная сущность. Хранится в `reports.data` (JSON), поля `id` и `title` продублированы колонками для поиска.

**Связи и реквизиты:**

| Поле | Тип | Смысл |
|------|-----|-------|
| `id` | string | Идентификатор |
| `title` | string | Наименование отчёта |
| `customerId` | string | Ссылка на `Customer.id` |
| `contractorId` | string | Ссылка на `Contractor.id` |
| `licenseId` | string | Ссылка на `License.id` |
| `contractId` | string | Ссылка на `Contract.id` |
| `coContractors` | `CoContractor[]` | Соисполнители (`{ contractorId }`) |
| `responsible` | string | Ответственный за отчёт |
| `secrecy` | `Secrecy` | Гриф: `нс`, `КТ`, `С`, `СС`, `ОВ` |
| `place` | string | Место проведения работ |
| `year` | string | Год |
| `govRegNumber` | string | Номер госрегистрации |

**Лицензия (копия реквизитов на момент отчёта):**
`licenseNumber`, `licenseDate`, `licenseExpiry`, `licensePdfUrl`, `licensePdfName`.

**Участок недр:**
`siteDescription`, `coordLat` (широта), `coordLon` (долгота), `depthLimit` (глубина, м).

**Добыча подземных вод:**
`extractionVolumeDayCurrent`, `extractionVolumeYearCurrent`,
`extractionVolumeDayPlan`, `extractionVolumeYearPlan`, `waterUseType`.

**Водоносный горизонт:**
`aquiferName`, `aquiferDepthTop` (кровля, м), `aquiferStaticLevel` (статический уровень, м),
`aquiferAllowableDrop` (допустимое понижение, м).

### 2.3 Блоки отчёта

Каждый раздел отчёта — отдельный «блок» со своей таблицей и своим типом данных.
Всего **24 блока**. Полный список — в `ALL_BLOCKS` (`src/lib/referencesApi.ts`)
и в словаре `BLOCKS` (`backend/references/index.py`).

Примеры структур:

**LabelData** (этикетка): `copyNumber`, `responsibleOverride`, `totalBooks`,
`totalFolders`, `bookNumber`, `bookName`.

**TitlePageData** (титульный лист): `approverPosition`, `approverName`, `approverDate`,
`customerPosition`, `customerName`, `customerDate`, `responsibleOverride`.

**AbstractData** (реферат): библиографические данные (`bibAuthors`, `bibTitle`, `bibYear`,
`bibPages`, `bibTables`, `bibIllustrations`), ключевые слова, методы работ (`methods`).

**MainSection[]** (основная часть) — иерархия разделов, каждый содержит массив блоков
`MainBlock`, где блок — один из типов: текст, изображение, таблица, ссылка на приложение.
Редактор таблиц — `TableBlockEditor.tsx`.

Остальные блоки (`intro`, `conclusion`, `study`, `illustrations`, `tables`,
`text_appendices`, `graphic_appendices`, `cost`, `references` и др.) — массивы записей
соответствующей структуры. Точные типы: `src/components/report/reportTypes.ts`.

### 2.4 Подписи разделов (section_meta)

Авторы и ответственные по каждой вкладке. Ключ составной: **отчёт + вкладка**,
поэтому у одного отчёта столько записей, сколько заполнено вкладок.

## 3. Связи между сущностями

Связи хранятся как идентификаторы внутри JSON и **не закреплены внешними ключами
на уровне БД** — целостность обеспечивает код приложения.

### 3.1 Схема связей

Слева — общие справочники, они переиспользуются разными отчётами.
Справа — данные, принадлежащие одному отчёту и живущие только вместе с ним.

```
        ОБЩИЕ СПРАВОЧНИКИ                        ДАННЫЕ ОДНОГО ОТЧЁТА
   (переиспользуются отчётами)              (удаляются вместе с отчётом)

  ┌───────────────────┐
  │     customers     │                    ┌──────────────────────────────┐
  │  id · name · inn  │                    │       report_label           │
  │ director· address │                    │       report_title_page      │
  └─────────┬─────────┘                    │       report_abstract        │
            │ owner_id                     │       report_intro           │
            │ (1:N)                        │       report_main_text       │
            ▼                              │       report_conclusion      │
  ┌───────────────────┐                    │       … всего 24 таблицы     │
  │     licenses      │                    ├──────────────────────────────┤
  │ id · number       │                    │ report_id  PK  ← reports.id  │
  │ site_name · type  │                    │ data       jsonb             │
  └─────────┬─────────┘                    │ updated_at timestamptz       │
            │                              └──────────────▲───────────────┘
            │ licenseId                                   │ 1:1
            │                                             │
  ┌───────────────────┐        ┌────────────────────┐     │
  │    contractors    │        │      reports       │─────┘
  │ id · name         │        ├────────────────────┤
  │ chief_geologist   │        │ id          PK     │     ┌──────────────────┐
  │ responsible       │◄───────│ title              │────►│  gkm_passports   │
  │ executors  jsonb  │ contr- │ data  jsonb:       │ 1:1 │ report_id PK     │
  └───────────────────┘ actorId│  ├ customerId  ────┼──►  │ massif · data    │
            ▲                  │  ├ contractorId    │     └──────────────────┘
            │ coContractors[]  │  ├ licenseId  ─────┼──►
            └──────────────────│  ├ contractId ─────┼──►  ┌──────────────────┐
                               │  ├ secrecy·place   │────►│report_section_meta│
  ┌───────────────────┐        │  └ year·coords…    │ 1:N │ report_id        │
  │     contracts     │◄───────│                    │     │ tab_id      ┐PK  │
  │ id · number· date │contract│                    │     │ data        ┘    │
  └───────────────────┘   Id   └────────────────────┘     └──────────────────┘
```

**Как читать:** `customers → licenses` — у одного заказчика много лицензий
(`licenses.owner_id`). Все четыре ссылки отчёта (`customerId`, `contractorId`,
`licenseId`, `contractId`) лежат **внутри JSON-поля** `reports.data`, а не в
колонках. Подписи разделов — единственная связь «один ко многим» внутри отчёта:
своя запись на каждую вкладку.

**Что удаляется вместе с отчётом:** всё, что в правой колонке — 24 блока,
паспорт ГКМ и все подписи разделов. Справочники слева остаются: они общие.

### 3.2 Путь правки от клавиатуры до базы

```
  пользователь печатает
          │
          ▼
     setValue()                    useReportBlock
          │
          ├──────────────► backupDraft()  ──► localStorage
          │                (только ручной режим)   "geo_draft_backup:{отчёт}:{блок}"
          │                                         срок жизни 7 дней
          ▼
   ┌──── режим? ─────┐
   │                 │
 авто              ручной
   │                 │
   │ пауза 600 мс    │ dirty = true → SaveBar → регистрация в draftRegistry
   │                 │                              │
   ▼                 ▼ кнопка «Сохранить»           │ используется для
 saveBlock() ◄───────┘                              │ «Сохранить всё (N)»,
   │                                                │ точек на вкладках,
   ▼                                                └─ вопроса при уходе
 POST /references  {resource:"block", block, reportId, data}
   │
   ▼
 INSERT ... ON CONFLICT (report_id) DO UPDATE
   │
   ▼
 успех → savedRef = value, dirty = false, clearDraftBackup()
```

Если вкладка закрылась между шагами «печатает» и «успех» — данные остались
в localStorage, и при следующем открытии раздела появится `RecoveryBanner`.

**Важно для развития.** Каскадного удаления в БД нет. При удалении отчёта все
связанные записи чистит фронтенд через `deleteAllBlocks()` — она удаляет
24 блока, паспорт ГКМ и все подписи разделов. **Добавили новый блок — обязательно
внесите его в `ALL_BLOCKS`**, иначе его данные останутся в базе «сиротами».

Фильтрация в интерфейсе: при выборе заказчика список лицензий сужается до тех,
у которых `ownerId` совпадает с выбранным заказчиком.

## 4. Схема базы данных

Схема: `t_p81502709_app_creator_project_`. Всего 31 таблица.

**Справочники** (обычные колонки): `customers`, `contractors`, `licenses`, `contracts`.
Индексы: по ИНН заказчика, по номеру лицензии, по владельцу лицензии.

**Отчёты:** `reports` — `id` (PK), `title`, `data` (jsonb), `created_at`, `updated_at`.

**Блоки разделов** — 24 таблицы по единому шаблону:

```sql
report_id  text PRIMARY KEY   -- один блок на отчёт
data       jsonb NOT NULL
updated_at timestamptz
```

**Паспорт ГКМ:** `gkm_passports` — `report_id` (PK), `massif` (код массива), `data` (jsonb).

**Подписи разделов:** `report_section_meta` — составной ключ `(report_id, tab_id)`, `data` (jsonb).

Миграции — в `db_migrations/`, применяются только вперёд, откатов нет.
Изменение схемы — исключительно через новую миграцию.

## 5. Backend API

Три функции. URL — в `backend/func2url.json`.

### 5.1 references

Универсальная функция: справочники, отчёты, блоки, паспорт, подписи.
Ресурс выбирается полем `resource` (или `kind` для справочников).

Подключение: `psycopg2`, простой протокол запросов, `autocommit`, `RealDictCursor`.
Все запросы параметризованы (`%s`) — защита от инъекций.
На все ответы ставится CORS `*`, метод `OPTIONS` обрабатывается первым.

Имена полей автоматически переводятся между `camelCase` (фронтенд)
и `snake_case` (база): `chiefGeologist` ↔ `chief_geologist`, `ownerId` ↔ `owner_id` и т.д.

**Справочники** (`kind`: `customers` | `contractors` | `licenses` | `contracts`)

| Метод | Запрос | Ответ |
|-------|--------|-------|
| GET (без параметров) | — | Все четыре справочника разом |
| POST | `{ kind, item }` | `{ item }` |
| DELETE | `{ kind, id }` | `{ ok: true }` |

**Отчёты** (`resource: "reports"`)

| Метод | Запрос | Ответ |
|-------|--------|-------|
| GET | `?resource=reports` или `&id=` | `{ reports: [] }` / `{ report }` |
| POST | `{ resource, item }` (нужен `item.id`) | `{ report }` |
| DELETE | `{ resource, id }` | `{ ok: true }` |

**Блоки** (`resource: "block"`)

| Метод | Запрос | Ответ |
|-------|--------|-------|
| GET | `?resource=block&block=&reportId=` | `{ data }` или `{ data: null }` |
| POST | `{ resource, block, reportId, data }` | `{ data }` |
| DELETE | `{ resource, block, reportId }` | `{ ok: true }` |

Запись — через `INSERT ... ON CONFLICT (report_id) DO UPDATE`, то есть повторное
сохранение обновляет запись. Неизвестное имя блока → ошибка 400.

**Паспорт ГКМ** (`resource: "passport"`): GET / POST (`massif`, `data`) / DELETE по `reportId`.

**Подписи разделов** (`resource: "section_meta"`)

| Метод | Запрос | Поведение |
|-------|--------|-----------|
| GET | `reportId` + `tabId` | Подписи одной вкладки |
| POST | `reportId`, `tabId`, `data` | Сохранить |
| DELETE | `reportId` + `tabId` | Удалить одну вкладку |
| DELETE | только `reportId` | **Удалить все подписи отчёта** (используется при удалении комплекта) |

### 5.2 merge-pdf

Сборка **печатного комплекта**: подшивает приложения к основному отчёту
и возвращает один готовый файл.

Запрос `POST`: `baseFile` (отчёт в base64) либо `baseUrl`, массив `attachments`
(`{url, title, filename}`) и `filename`.
Ответ: `{url, filename, pages, merged, skipped[]}` — ссылка на готовый файл,
число страниц и перечень того, что подшить не удалось.

Особенности:

- PDF-приложения подшиваются как есть, постранично.
- **Карты, схемы и изображения** переводятся в PDF: вписываются в лист A4,
  широкие листы автоматически кладутся горизонтально (альбомная ориентация).
- Сбой одного вложения не срывает сборку — файл попадает в `skipped`,
  остальное подшивается. Пользователь видит, чего не хватает.
- Результат кладётся в S3 (`geo-merged/`), отдаётся ссылкой CDN.

Библиотеки: `pypdf` (склейка), `pillow` (изображения), `boto3` (хранилище).

### 5.3 upload-file

Приём файлов (PDF лицензий, изображения, приложения). Файл передаётся
в теле запроса в кодировке base64, складывается в S3-бакет `files`,
в ответ возвращается публичная ссылка CDN.

### 5.4 Тесты

`backend/references/tests.json` — 19 тестов, покрывают все ресурсы и методы.
**Правило: после любой правки backend запускайте синхронизацию — все тесты должны проходить.**

## 6. Клиентский слой API

`src/lib/referencesApi.ts` — единственная точка обращения к backend.

| Функция | Назначение |
|---------|------------|
| `fetchBlock(block, reportId)` | Загрузить раздел |
| `saveBlock(block, reportId, data)` | Сохранить раздел |
| `deleteAllBlocks(reportId)` | Удалить все данные отчёта: 24 блока + паспорт + подписи |
| `ALL_BLOCKS` | Список всех блоков — **источник правды при удалении** |
| `fetchSectionMeta(reportId, tabId)` | Подписи вкладки |

Хуки-обёртки: `useReferences` (справочники), `useReports` (список комплектов),
`useReportBlock` (раздел отчёта).

## 7. Механика сохранения данных

Всё держится на хуке `useReportBlock` (`src/lib/useReportBlock.ts`).

```ts
const block = useReportBlock<T>(blockName, reportId, initial, legacyKey?, { manual });
```

Возвращает: `value`, `setValue`, `loading`, `saving`, `reload`, `dirty`, `save`,
`revert`, `recovery`, `restoreBackup`, `dismissBackup`.

### Два режима

**Автоматический** (по умолчанию) — правка уходит в базу сама через **600 мс**
после последнего изменения. Применяется к спискам и файлам, где нет свободного текста.

**Ручной** (`manual: true`) — правки копятся, запись только по кнопке «Сохранить».
Здесь работают признак `dirty`, откат `revert()`, панель `SaveBar`
и страховочные копии в браузере.

Ручной режим включён у **7 блоков**:

| Блок | Где объявлен | Раздел |
|------|--------------|--------|
| `label` | `pages/ReportPage.tsx` | Этикетка |
| `title_page` | `pages/ReportPage.tsx` | Титульный лист |
| `abstract` | `pages/ReportPage.tsx` | Реферат |
| `intro` | `report/IntroSection.tsx` | Введение |
| `main_text` | `report/MainSection.tsx` | Основная часть |
| `conclusion` | `report/ConclusionSection.tsx` | Заключение |
| `study` | `report/StudySection.tsx` | Изученность (раздел комплекта) |

Три первых блока подключены прямо в `ReportPage`, остальные — внутри своих
компонентов. Проверить актуальный список: `rg "manual: true" src/`.

### Внутренние механизмы

| Механизм | Роль |
|----------|------|
| `savedRef` | Последнее сохранённое значение — эталон для сравнения и отката |
| `dirty` | Текущее значение отличается от `savedRef` |
| `pendingSave` | Правка ждёт записи по таймеру; при уходе с раздела дописывается немедленно, чтобы не потеряться |
| `ready` | Загрузка завершена — до этого правки не пишутся в базу |
| `touched` | Пользователь начал править до окончания загрузки (защита от затирания ввода) |
| `legacyKey` | Перенос данных из старого браузерного хранилища при первом открытии |

## 8. Защита от потери данных

Четыре независимых рубежа.

**1. Страховочная копия в браузере** — `src/lib/draftBackup.ts`.
Пока правки не записаны, они дублируются в localStorage.

- Ключ: `geo_draft_backup:{reportId}:{block}`
- Содержимое: `{ data, savedAt }`
- Срок жизни: **7 дней**, протухшие копии игнорируются и удаляются
- Копия стирается после успешной записи в базу и при откате
- `clearReportBackups(reportId)` — чистка при удалении отчёта

Если вкладка закрылась до сохранения, при следующем открытии раздела появится
`RecoveryBanner` с предложением восстановить и датой правок. Плашка не показывается,
если копия совпадает с тем, что уже в базе.

**2. Реестр черновиков** — `src/lib/draftRegistry.ts`.
Все разделы с несохранёнными правками регистрируются централизованно.

`registerDraft` / `unregisterDraft` / `hasUnsaved()` / `saveAllDrafts()` /
`revertAllDrafts()` / `subscribeDrafts()`.

Это даёт кнопку «Сохранить всё (N)» и корректную реакцию на уход со страницы.
`saveAllDrafts()` сохраняет разделы параллельно — сбой одного не мешает остальным.

Соответствие блоков и вкладок задаёт `DRAFT_TO_TAB`: введение, основная часть
и заключение — три отдельных блока, но одна вкладка «Текстовая часть».

**3. Предупреждения при уходе.** Смена вкладки с несохранёнными правками →
`UnsavedChangesModal` (сохранить / не сохранять / остаться). Закрытие браузера →
системное предупреждение.

**4. Отметки на вкладках** — `useDirtyTabs()` подсвечивает точкой вкладки
с несохранёнными правками.

## 11. Темы оформления

Две схемы, переключатель — в шапке каждого экрана (`ThemeToggle`).

- **Тёмная** (по умолчанию): тёмный фон, янтарный акцент.

Реализация — `src/lib/useTheme.ts`. Светлая тема включается классом
`theme-light` на корневом элементе, который переопределяет CSS-переменные
из `src/index.css`. Выбор хранится в localStorage (`geo_theme`) и применяется
до первого рендера, чтобы не было вспышки.

**Правило для новых компонентов:** используйте только переменные темы
(`bg-card`, `text-foreground`, `text-geo-amber`, `border-border`), не пишите
цвета жёстко — иначе элемент «выпадет» из одной из тем.

## 13. Экспорт PDF

`src/components/report/exportPdf.ts`.

- `collectPdfData(...)` — собирает данные всех разделов в единую структуру
- `exportToPdf(data)` — рендерит и сохраняет файл

Библиотека `html2pdf.js` подгружается динамически — только в момент экспорта,
чтобы не утяжелять загрузку приложения. Формат A4, книжная ориентация.
Стили страниц печати — класс `.pdf-page` в `src/index.css` (белый фон,
Times New Roman, поля по ГОСТ).

### Как устроен экспорт

```
кнопка «Экспорт PDF»
   │
   ├─ 1. hasUnsaved() → saveAllDrafts()      ← несохранённые правки пишутся в базу
   │       сбой → экспорт отменяется, показывается ошибка
   │
   ├─ 2. collectPdfData()                    ← читает 20 блоков ИЗ БАЗЫ параллельно
   │       при недоступности блока → копия из localStorage → пустое значение
   │
   ├─ 3. рендер <ReportPdfView> в скрытый контейнер (210 мм), пауза 400 мс
   │
   └─ 4. html2pdf → сохранение файла
           контейнер удаляется в любом случае (finally)
```

**Важно:** документ собирается **из базы**, а не из состояния экрана. Поэтому
перед сборкой обязательно выполняется запись черновиков — иначе в PDF попадёт
предыдущая версия разделов.

### Что попадает в документ

Выгружается **19 разделов** в порядке ГОСТ. Состав задаёт `ReportPdfView`:

1. Этикетка · 2. Титульный лист · 3. Список исполнителей · 4. Реферат ·
5. Копия задания · 6. Содержание · 7. Список иллюстраций · 8. Список таблиц ·
9. Текстовые приложения · 10. Графические приложения · 11. Термины ·
12. Текстовая часть (введение + основная + заключение) · 13. Список источников ·
14. Метрологическая экспертиза · 15. Патентные исследования · 16. Рецензии ·
17. Протокол рассмотрения · 18. Справка о стоимости · 19. Акты передачи

Разделы без данных пропускаются автоматически — компоненты возвращают `null`,
пустых страниц в документе не появляется.

**Два вида разделов в PDF:**

- *Содержательные* — текст и таблицы выводятся полностью
  (`PdfFrontPages`, `PdfTextPartPage`, `PdfAppendixPages`).
- *Разделы-вложения* — метрология, патенты, рецензии, протокол, стоимость,
  акты, копия задания. Сами документы хранятся файлами в S3, вшить их
  в PDF нельзя, поэтому выводится **опись**: наименование, имя файла,
  дата приобщения и пометка, что документ приложен отдельно. Компоненты —
  `PdfExtraPages.tsx`.

**Не выгружается:** машиночитаемая версия — это служебная вкладка,
печатного представления не имеет.

### Печатный комплект (склейка приложений)

Кнопка «Комплект к печати» рядом с экспортом. Итог — **один файл**, готовый
к распечатке: отчёт и все приложения подряд.

```
      «Комплект к печати»
              │
              ├─ сохранение черновиков (как при обычном экспорте)
              ├─ collectPdfData()      → данные всех разделов
              ├─ collectAttachments()  → список вложений В ПОРЯДКЕ ГОСТ
              ├─ renderPdfBlob()       → основной отчёт как PDF (без сохранения)
              │
              └─ POST merge-pdf {baseFile, attachments}
                        │
                        ├─ PDF подшиваются постранично
                        ├─ карты/схемы → переводятся в A4, широкие — горизонтально
                        └─ ссылка на готовый файл + список неподшитого
```

Порядок вложений задаёт `collectAttachments.ts` — по ГОСТ: копия задания,
текстовые приложения по номерам, графические приложения (карты, схемы),
метрология, патенты, рецензии, протокол, справка о стоимости, акты передачи.

**Важно:** описи разделов-вложений в основном отчёте остаются — они играют роль
оглавления приложений, а сами документы идут следом.

### Известные ограничения

- Основная часть отчёта рендерится через `html2canvas` — страницы получаются
  растровыми (текст не выделяется и не ищется). Подшитые PDF-приложения при этом
  сохраняют исходное качество и текстовый слой. При переходе к объёмным отчётам
  стоит рассмотреть серверную генерацию и основной части.
- Сборка комплекта выполняется в облачной функции с ограничением по времени.
  Если приложений станет очень много или они окажутся тяжёлыми, потребуется
  увеличить таймаут функции (Ядро → Функции → merge-pdf → Настройки)
  либо перейти к фоновой обработке.
- Нумерация страниц в содержании берётся из блока `contents_pages`
  и проставляется вручную, автоматического пересчёта нет.

## 14. Как развивать проект

**Добавить новый раздел отчёта:**

1. Миграция: таблица `report_<имя>` по шаблону (`report_id` PK, `data` jsonb, `updated_at`)
2. `backend/references/index.py` — добавить блок в словарь `BLOCKS`
3. `backend/references/tests.json` — тест на новый блок, синхронизировать backend
4. `src/lib/referencesApi.ts` — добавить имя блока в **`ALL_BLOCKS`** (иначе не удалится с отчётом)
5. `src/components/report/reportTypes.ts` — тип данных и запись в `TABS`
6. Компонент раздела: `useReportBlock` + `SaveBar` (если ручной режим)

**Добавить поле в карточку комплекта:** дополнить `ReportData` в `src/types/geo.ts` —
миграция не нужна, данные лежат в JSON. Затем поле в форме `ReportFormFields`.

**Добавить справочник:** миграция с таблицей → словарь `KINDS` в backend →
при необходимости `FIELD_MAP` для полей из нескольких слов → тип и хук на фронтенде.

**Чего избегать:**

- SQL и секреты на фронтенде
- Жёстко прописанных цветов вместо переменных темы
- Новых блоков без записи в `ALL_BLOCKS`
- Правки схемы БД мимо миграций
- Файлов больше ~400 строк — выносите части в отдельные компоненты

**Отладка:** логи фронтенда и функций доступны через инструмент логов;
состояние базы — через SQL-запросы к схеме проекта.

**Чек-лист перед завершением доработки:**

1. Сборка проходит без ошибок
2. Тесты backend зелёные (если менялся backend)
3. Новый блок внесён в `ALL_BLOCKS`
4. Новые элементы интерфейса используют переменные темы и корректны в обеих схемах
5. **Документация обновлена, строка добавлена в журнал ниже**

## 15. План развития

Направления, согласованные с заказчиком. **Пока не реализованы**, запланированы
на будущие этапы. Раздел ведётся, чтобы текущие решения не противоречили этим целям.

### 15.1 Роли пользователей

Сейчас система однопользовательская: все имеют полный доступ, авторства правок нет.
Планируется разделение как минимум на две роли:

- **Заполняющий** — вносит данные отчёта, изученности, первичной информации.
- **Проверяющий** — последовательно принимает разделы и выставляет замечания.

*Что потребуется:* учётные записи и вход в систему, таблица пользователей,
привязка отчёта к организации, признак автора у правок.
Заголовки авторизации на этой платформе проксируются: фронтенд отправляет
`Authorization`, backend читает `X-Authorization`.

### 15.2 Пошаговая проверка с замечаниями

Проверка идёт **по каждому разделу отдельно** — отчёта, изученности, первички.
У раздела появляется статус и история замечаний.

*Ориентировочная модель:* статус раздела (черновик → на проверке → замечания →
принят) и таблица замечаний, привязанных к паре «отчёт + раздел», с автором,
датой, текстом и признаком устранения.

*Хорошая новость:* архитектура к этому готова. Каждый раздел уже отдельная
сущность с ключом «отчёт + блок», а для вкладок есть `report_section_meta`
с составным ключом «отчёт + вкладка» — замечания ложатся на ту же схему.
Индикаторы состояния разделов тоже есть — механизм подсветки вкладок
(`useDirtyTabs`) можно расширить со «есть правки» до «есть замечания».

### 15.3 Распознавание сканов готовых отчётов

Загрузка скана бумажного отчёта и автоматическое раскладывание его содержимого
по нашим моделям разделов.

*Что потребуется:* распознавание текста, разбиение по разделам ГОСТ,
сопоставление с блоками, обязательный экран ручной проверки перед записью —
распознавание не бывает стопроцентным.

*Замечания по реализации:* обработка скана долгая, а у облачных функций
ограничение по времени выполнения — потребуется фоновая обработка с очередью,
а не один запрос. Файлы уже умеем принимать (`upload-file` → S3).
Структура блоков (`ALL_BLOCKS`) станет целевой схемой для раскладки.
